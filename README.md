# 📌 기능 요구 사항
## 1. 입력 기능
- [X] 사용자가 경주할 자동차 이름들을 입력한다(쉼표로 구분)
- [x] 사용자가 시도할 횟수를 입력한다.
<br>

## 2. 유효성 검사 기능
- [x] 입력된 자동차 이름이 5자를 초과하는 경우 IllegalArgumentException 발생
- [x] 입력된 자동차 이름이 비어있거나, 공백만 있는경우 IllegalArgumentException 발생
- [x] 시도할 횟수의 숫자가 숫자가 아니거나 1 미만의 숫자일 경우 IllegalArgumentException 발생
- [x] 시도할 횟수의 숫자가 공백으로 들어오는 경우 IllegalException 발생
<br>

## 3. 게임 매인 기능
- [x] 각 자동차 이름기반으로 car 객체 생성(이름 + 현재 위치)
- [x] car 객체는 무작위 값이 4 이상이 나오면 1칸 전진한다.
- [x] car 객체는 무작위 값이 3 이하일 경우 멈추고 현재 위치를 유지한다.
- [x] 모든 시도가 끝난 후, 가장 멀리 이동한 차를 우승자로 선정한다
<br>

## 4. 출력 기능
- [x] 각 시도가 끝날 때마다 현재 모든 자동차 위치를 '-'(1칸)으로 표시한다. (이름 : -- 형태)
- [x] 최종 우승자를 '최종 우승자 : 이름' 형식으로 출력한다. (여러명인 경우 이름칸에 쉼표로 구분)

# 💡What I Learn
- Test가 요구사항명세서 처럼 작동하기 때문에 에러메시지를 정확히 일치시켜줘야한다.
  (예를들어 TryCountTest에서의 에러메시지와 TryCount에서의 에러메세지는 정확히 동일하게 맞추어주어야한다.)

- depth2를 지키기 위해서는 책임을 더 단순하고 자세하게 분리해야한다. 뿐만 아니라 값을 그대로 사용하지 않고 의미있는 객체(TryCount,Car)로 캡슐화해서 Controller는 검증을 어떻게 하는지모르고 받아서 사용만 가능하게 한다(객체지향)
- TDD 방식을 지키는게 무척 어색하고 어려웠지만 기능이 추가될 때 버그를 놓치지않고 자동으로 테스트하기 위해선 TDD가 필수!
(거기다 의도적이고 자세한 예외상황까지 조작 가능)

- 랜덤을 활용한것처럼 불확실한 기능은 TDD적용이 어려운데, 이를 위해 move메서드를 두가지 경우로 나누어 분리했다. 불확실한 부분과 실제로 구현되는 핵심 로직을 분리해서 TDD로 검증할 수 있다.

- findMaxPostion이나 findWinner와 같은 메서드에서 익숙한 명령형 프로그래밍이아닌 선언형 방식으로 람다식과 stream API를 사용해봄.
  (찾고싶은 과정보다 무엇을 원하는지, 특히 데이터의 흐름이 명확하게 보이고 코드가 간단해진다)

- 예외테스트를 보면 assertThatThrownBy를 사용하는데 메서드 실행시 IllegalArgumentExceptional throw되기를 원하는 것으로
try-catch로 내부에서 잡아버리면 안된다.
